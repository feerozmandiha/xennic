- **ID:** ADR-027

## Context

Xennic یک پلتفرم مهندسی برق با هسته‌ی مرکزی است: `apps/api` (NestJS/Fastify)، دیتابیس PostgreSQL واحد (Prisma)، و سرویس‌های `vision-service`، `engineering-service` و `ai-service`.

دو نیاز جدید محصولی مطرح شد:

1. **Bill-Bot** — ربات تحلیل قبض برق (تلگرام/بله) که از `vision-service` برای OCR و از موتور تعرفه‌ی ۱۴۰۵ استفاده می‌کند (طراحی کامل در `docs/bill-bot/`، اسکلت در `services/bill-bot/`).
2. **اپ موبایل (آینده)** — باید از اطلاعات موجود پلتفرم (کاربران، مشاوره‌ها، محاسبات، دانش) مصرف کند.

سؤال معماری: کانال‌های جدید باید **داخل** هسته‌ی Xennic ساخته شوند، **جدا** (با دیتابیس/بک‌اند مستقل)، یا **ترکیبی**؟

## Decision

**معماری «پلتفرم + کانال‌ها» (Platform + Channels):** کانال‌ها (Bot، Mobile، Web) به‌عنوان **سرویس‌های مصرف‌کننده‌ی مستقل** از یک **هسته‌ی مرکزی واحد** (API + دیتابیس واحد) تغذیه می‌شوند.

```
┌──────────────────────────────────────────────┐
│             XENNIC CORE (مرکزی)               │
│  API 3000 · Postgres واحد · vision · AI      │
└──────┬──────────────┬──────────────┬─────────┘
       │              │              │
  ┌────▼────┐    ┌────▼─────┐   ┌────▼────────┐
  │ Web 3001│    │ Bill-Bot │   │ Mobile App  │
  │ (موجود) │    │ (سرویس  │   │ (آینده)     │
  └─────────┘    │  مستقل)  │   └─────────────┘
                 └──────────┘
```

### قواعد الزامی

1. **داده‌ی اصلی فقط در هسته‌ی مرکزی** — هیچ کانالی دیتابیس اصلی خودش را نمی‌سازد (SQLite در Bill-Bot فقط برای نشست‌های گذرای چت).
2. **دسترسی کانال‌ها فقط از طریق API مرکزی** — با JWT کاربر (موبایل/وب) یا API Key سرویس (ربات).
3. **مصرف vision/engineering/AI از طریق اندپوینت‌های موجود** — نه اتصال مستقیم به دیتابیس سرویس‌های پایتونی.
4. **استقرار مستقل** — کانال‌ها جدا deploy و scale می‌شوند؛ خرابی یکی روی دیگری اثر ندارد.
5. **قابلیت مشاهده‌ی یکسان** — هر داده‌ی ثبت‌شده از هر کانال، در همه‌ی کانال‌ها دیده می‌شود (مثلاً درخواست‌های مشاوره).

## Consequences

### مثبت

- ✅ استفاده‌ی کامل از بک‌اند/دیتابیس موجود (نیاز شما) — بدون دیتابیس موازی
- ✅ اپ موبایل بدون بک‌اند جدید (همان JWT و اندپوینت‌ها)
- ✅ مقیاس‌پذیری و استقرار مستقل کانال‌ها
- ✅ داده‌ی یکپارچه (وب/موبایل/ربات همان رکوردها)

### منفی / هزینه

- ⚠️ کانال‌ها به API مرکزی وابسته‌اند (در دسترس نبودن API = خرابی کانال) — با رزیلینس (retry/backoff) مدیریت می‌شود
- ⚠️ نیاز به اندپوینت‌های جدید برای موارد کانال‌محور (مثلاً `/consultations/bot`) — به‌صورت feature جدا

## Alternatives Considered

1. **همه در یک برنامه (Monolith)**: رد شد — long-polling تلگرام/webhook به هسته گره می‌خورد؛ deploy پرریسک.
2. **دیتابیس/بک‌اند جدا برای هر کانال**: رد شد — با نیاز «داده‌ی مرکزی مشترک» و اپ موبایل در تضاد است.
3. **فقط نگه‌داشتن Bill-Bot بدون مرج**: رد شد — کد و مستندات آماده بدون ارزش ماندن.
