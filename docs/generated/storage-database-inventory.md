# مستند ساختار پایگاه داده پلتفرم ذخیره‌سازی (Storage Database Inventory)

========================================================================

**شناسه سند:** XENNIC-STORAGE-DB-001  
**تاریخ سند:** ۲۸ تیر ۱۴۰۵ (2026-07-18)  
**نسخه:** 1.0.0  
**مسئول تدوین:** دستیار معماری و حاکمیت Storage (شناسه: `XENNIC-STORAGE-ARCH-001`)  
**وضعیت پایگاه داده:** آماده توسعه فاز یک

این مستند حاوی شرح تفصیلی جداول موجود و اصلاحات ساختاری لازم در سطح لایه داده پروژه زنیک (Prisma ORM) به همراه تحلیل کلیدها، نمایه‌ها و گاردها می‌باشد.

---

## ۱. ساختار جداول موجود در فایل شمای پریزما (`prisma/schema.prisma`)

در حال حاضر دو جدول مستقل برای نگهداری فایل‌ها و نسخه‌ها تعریف شده است:

### ۱.۱. جدول فایل‌ها (`files`)

- **نام مدل:** `files`
- **هدف:** نگهداری ردیف‌های فراداده فایل‌های آپلود شده در سیستم.

| نام ستون در دیتابیس | نوع داده در Prisma | نوع داده در PostgreSQL | وضعیت Nullable | توضیحات بیزینسی                                  |
| :------------------ | :----------------- | :--------------------- | :------------- | :----------------------------------------------- |
| **`id`**            | `String`           | `uuid`                 | خیر (PK)       | شناسه منحصربه‌فرد کلید اصلی فایل                 |
| **`workspace_id`**  | `String`           | `text`                 | خیر (FK)       | ارجاع به جدول فضاهای کاری (`workspaces`)         |
| **`bucket`**        | `String`           | `text`                 | خیر            | نام باکت هدف در MinIO (محدود به ۶ نام استاندارد) |
| **`path`**          | `String`           | `text`                 | خیر            | مسیر نسبی فایل در باکت پس از شناسه مستأجر        |
| **`filename`**      | `String`           | `text`                 | خیر            | نام فیزیکی فایل تولیدشده توسط سیستم (UUID)       |
| **`original_name`** | `String`           | `text`                 | خیر            | نام اصلی فایل که توسط کاربر ارسال شده است        |
| **`extension`**     | `String`           | `text`                 | خیر            | پسوند فایل (مانند pdf, png) به صورت حروف کوچک    |
| **`mime_type`**     | `String`           | `text`                 | خیر            | نوع استاندارد رسانه‌ای فایل (Mime-Type)          |
| **`size`**          | `BigInt`           | `bigint`               | خیر            | سایز فایل بر حسب بایت                            |
| **`checksum`**      | `String?`          | `text`                 | **بله**        | هش تولید شده از روی فایل (مبتنی بر SHA-256)      |
| **`uploaded_by`**   | `String`           | `text`                 | خیر (FK)       | شناسه کاربر آپلودکننده فایل (`users`)            |
| **`created_at`**    | `DateTime`         | `timestamp`            | خیر            | زمان بارگذاری فایل (پیش‌فرض: `now()`)            |
| **`deleted_at`**    | `DateTime?`        | `timestamp`            | **بله**        | زمان حذف نرم فایل در صورت مخفی‌سازی              |

- **نمایه‌ها (Indexes):**
  - `@@index([workspace_id])` جهت افزایش سرعت جست‌وجوی فایل‌های متعلق به یک مستأجر.
  - `@@index([uploaded_by])` جهت فیلتر و گزارش‌گیری فایل‌های آپلودی هر کاربر.
  - `@@index([mime_type])` برای بهینه‌سازی فیلتر نوع فایل‌ها.

### ۱.۲. جدول نسخه‌ها (`file_versions`)

- **نام مدل:** `file_versions`
- **هدف:** ثبت ارجاع‌های نسخه‌های تاریخی تغییریافته فایل‌ها.

| نام ستون در دیتابیس | نوع داده در Prisma | نوع داده در PostgreSQL | وضعیت Nullable | توضیحات بیزینسی                                |
| :------------------ | :----------------- | :--------------------- | :------------- | :--------------------------------------------- |
| **`id`**            | `String`           | `uuid`                 | خیر (PK)       | کلید اصلی شناسه نسخه                           |
| **`file_id`**       | `String`           | `text`                 | خیر (FK)       | کلید خارجی متصل به شناسه فایل پدر (`files.id`) |
| **`version`**       | `Int`              | `integer`              | خیر            | شماره افزایشی نسخه فایل (شروع از ۱)            |
| **`path`**          | `String`           | `text`                 | خیر            | مسیر باینری فایل نسخه در باکت                  |
| **`checksum`**      | `String?`          | `text`                 | **بله**        | هش شناسه یکپارچگی فایل نسخه جدید               |
| **`created_at`**    | `DateTime`         | `timestamp`            | خیر            | زمان آپلود شدن نسخه جدید                       |

- **قوانین حذف ردیف (Cascade Delete):**
  - ارتباط با `files` به صورت `onDelete: Cascade` است؛ به این معنی که با حذف سخت یک فایل اصلی، تمام ردیف‌های مربوط به نسخه‌های قدیمی‌تر آن نیز به صورت فیزیکی از جدول دیتابیس حذف خواهند شد.

## ۲. گسست دیتابیسی و نیازهای اصلاح شمای ارتباطی (Database Gap Registry)

برای جاری ساختن معماری جامع پلتفرم، تغییرات ساختاری زیر روی شمای پایگاه داده طراحی و پیشنهاد می‌شود:

```
  ┌───────────────────────────────────────────────────────────┐
  │                        workspaces                         │
  └─────────────────────────────┬─────────────────────────────┘
                                │ (logo_file_id ──► files.id)
                                ▼
  ┌───────────────────────────────────────────────────────────┐
  │                           files                           │
  └─────────────────────────────▲─────────────────────────────┘
                                │ (file_id ──► files.id)
         ┌──────────────────────┼──────────────────────┐
         ▼                      ▼                      ▼
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│   file_versions  │  │knowledge_document│  │   calculations   │
└──────────────────┘  └──────────────────┘  └──────────────────┘
```

### الف) اتصال مستقیم کارخانه دانش به جدول فایل‌ها

در مدل `knowledge_documents` ستون `storage_path` باید به عنوان فیلد فرعی در نظر گرفته شده و فیلد اصلی ارتباطی به صورت زیر تعریف شود:

```prisma
model knowledge_documents {
  // ...
  file_id      String?           @unique
  file         files?            @relation(fields: [file_id], references: [id])
  // ...
}
```

### ب) اتصال پیوست‌های محاسبات مهندسی

در مدل `calculations` ورودی‌ها و خروجی‌های محاسباتی به جدول فایل‌ها لینک داده می‌شوند:

```prisma
model calculations {
  // ...
  input_file_id   String?
  output_file_id  String?

  input_file      files?   @relation("CalculationInputs", fields: [input_file_id], references: [id])
  output_file     files?   @relation("CalculationOutputs", fields: [output_file_id], references: [id])
  // ...
}
```

### ج) تصویر لوگوی فضاهای کاری و آواتار کاربران

- **در مدل `workspaces`:**
  ```prisma
  logo_file_id    String?   @unique
  logo_file       files?    @relation("WorkspaceLogo", fields: [logo_file_id], references: [id])
  ```
- **در مدل `users`:**
  ```prisma
  avatar_file_id  String?   @unique
  avatar_file     files?    @relation("UserAvatar", fields: [avatar_file_id], references: [id])
  ```

## ۳. سناریوی اجرای پچ مهاجرت دیتابیس (DB Migration Plan)

از آنجایی که سیستم در حال توسعه است، برای اعمال تغییرات بدون گسست یا خرابی داده‌های موجود، مهاجرت‌ها به صورت زیر تایید صلاحیت می‌شوند:

1. **گام اول:** تولید پچ پریزما جهت ایجاد ارتباطات جدید به شکل فیلدهای اختیاری (`Optional / Nullable`). این اقدام جلوی بروز هرگونه عدم انطباق روی رکوردهای قبلی دیتابیس را می‌گیرد.
2. **گام دوم:** اجرای اسکریپت بک‌آپ‌گیری از داده‌ها به صورت خودکار قبل از اعمال مهاجرت به وسیله اسکریپت‌های زیرساختی ریکاوری.
3. **گام سوم:** اعمال مهاجرت ساختاری پایگاه داده از طریق اجرای دستور زیر به کمک فرآیندهای امن توسعه:
   `pnpm prisma migrate dev --name add_unified_storage_relations`
