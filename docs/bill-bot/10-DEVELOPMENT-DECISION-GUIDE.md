## ۱. خلاصه مدیریتی (یک‌صفحه‌ای)

**پروژه:** ربات گفتگوگر تحلیل قبض برق مشترکان روی دو پیام‌رسان **تلگرام** و **بله** — دریافت قبض (عکس / تصویر / PDF) ← استخراج کامل اطلاعات ← نمایش.

**درخواست فعلی کارفرما (دامنه MVP):** فقط «استخراج اطلاعات و نمایش جدول» در چت؛ **بدون هیچ ذخیره‌سازی** (فایل، متن OCR، داده‌های استخراجی) تا پس از تست و بررسی، ربات به endpointهای پروژه Xennic متصل و توسعه کامل شود.

**یافته‌های کلیدی مطالعه:**

1. بسته کامل مستندات پروژه (۹ سند + README) از قبل در `docs/bill-bot/` موجود است و شامل: چشم‌انداز، الزامات، معماری، مدل داده قبض (۲۹ فیلد)، موتور تعرفه ۱۴۰۵، موتور تحلیل، گزارش PDF، امنیت/حریم خصوصی و برنامه اقدام.
2. اسکلت کامل سرویس در `services/bill-bot/` پیاده‌سازی شده است: آداپتور دوگانه تلگرام/بله، استخراج‌گر regex فارسی، کلاینت vision-service، موتور تعرفه ۱۴۰۵، تحلیل‌گر، مولد گزارش، ماشین حالت مکالمه — با **۳۰ تست واحد سبز** (Node ≥ 22 بدون build).
3. دامنه درخواستی کارفرما **کوچک‌تر از** آن چیزی است که اسکلت فعلی ارائه می‌دهد (اسکلت شامل تحلیل تعرفه، PDF و مشاوره با ذخیره‌سازی نیز هست). بنابراین تصمیم اصلی این است: **اسکلت موجود را به MVP برش دهیم (گزینه A) یا از صفر MVP مستقل بنویسیم (گزینه B)**.
4. یک **باگ مسیر endpoint** در کد فعلی شناسایی شد: کلاینت vision ربات به‌جای `POST /api/v1/vision/bill/read` (مسیر واقعی سرویس بینایی) به `POST /vision/bill/read` می‌زند؛ در نتیجه مسیر اصلی OCR عملاً همیشه fallback می‌شود و باید پیش از هر تست میدانی اصلاح شود (بخش ۶).

**توصیه:** گزینه A — برش اسکلت موجود به دامنه MVP با برآورد **۱ تا ۲ روز کاری** تا تست میدانی؛ سپس فاز اتصال کامل به Xennic (کالیبراسیون OCR + یکپارچه‌سازی) و در نهایت برگشت تدریجی قابلیت‌های تعرفه/PDF/مشاوره طبق مستندات موجود.

## ۴. دامنه درخواستی کارفرما (MVP) و شکاف با کد فعلی

> **هدف MVP:** کاربر در تلگرام/بله، عکس قبض یا فایل تصویر/PDF می‌فرستد ← ربات از طریق endpoint بینایی Xennic (یا OCR محلی) اطلاعات را استخراج می‌کند ← **فقط جدول «عنوان | مقدار» در چت نمایش می‌دهد** ← **هیچ داده‌ای ذخیره نمی‌شود** ← تست و بررسی ← سپس توسعه با اتصال کامل به Xennic.

### ۴.۱ چک‌لیست حفظ / تعلیق / حذف در MVP

| قابلیت | در MVP | توضیح |
| --- | :---: | --- |
| دریافت `document` (PDF/JPG/PNG/WEBP) و `photo` تا ۱۰MB | ✅ حفظ | FR-101/102 |
| دانلود فایل از سرور پیام‌رسان (در RAM) | ✅ حفظ | پس از پردازش، بایت‌ها آزاد شوند |
| فراخوانی vision-service و استخراج | ✅ حفظ | پس از اصلاح مسیر endpoint |
| استخراج محلی regex (fallback) | ✅ حفظ | در نبود vision-service |
| **نمایش جدول کامل** (شناسه‌ای / دوره و قرائت / ریز مبالغ) | ✅ حفظ | خروجی اصلی MVP (سند ۰۴، ۲۹ فیلد) |
| علامت‌گذاری فیلدهای کم‌اطمینان با ⚠️ | ✅ حفظ | تصمیم «دقیق یا نامشخص» |
| دستورها `/start` `/help` `/bill` `/cancel` | ✅ حفظ | بدون /status، /requests، /privacy وابسته به ذخیره |
| تحلیل تعرفه ۱۴۰۵ (پله‌ها، الگو، توصیه‌ها) | ⏸️ تعلیق | در فاز ۲ بدون تغییر کد فعال می‌شود |
| لایه LLM | ⏸️ تعلیق | در MVP اتصال ندارد |
| گزارش PDF / HTML | ⏸️ تعلیق | دکمه‌ها حذف یا غیرفعال |
| مشاوره PV / تلفنی | ⛔ تعلیق | نیازمند ذخیره‌سازی است — مغایر با «بدون ذخیره» |
| ذخیره‌سازی (ConsultationStore / DATA_DIR / SQLite) | ⛔ **غیرفعال** | هیچ فایلی روی دیسک نوشته نشود |
| ادمین (`/requests`، اعلان) | ⛔ تعلیق | فاز ۲ |
| متریک/لاگ | ✅ سبک | لاگ بدون PII کافی است |

### ۴.۲ تعریف «بدون ذخیره‌سازی» (محدوده اجرایی)

- نشست‌های گفتگو فقط در حافظه (Map) — پس از ری‌استارت ربات، هیچ اثری باقی نیست.
- فایل دریافتی فقط به‌صورت بایت در RAM؛ پس از پاسخ به کاربر آزادسازی می‌شود.
- `DATA_DIR` ساخته/نوشته نشود؛ ماژول store در startup مقداردهی نگردد.
- متن OCR خام (`rawText`) فقط در حافظه همان نشست و در لاگ‌ها **هیچ‌گاه** (شناسه‌ها ماسک شوند).
- دکمه‌ها و دستورهای وابسته به ذخیره (`/status`، `/requests`، مشاوره، PDF کش‌شده) در دسترس نباشند.

## ۵. اتصال به endpointهای پروژه Xennic

### ۵.۱ سرویس بینایی (`workspace/services/vision-service` — پورت 8003)

مسیر واقعی روت‌ها (با پیشوند `api/v1` — تأیید شده از `app/api/__init__.py`):

| متد و مسیر | ورودی | خروجی |
| --- | --- | --- |
| `GET /health` | — | `{status, service, version}` |
| `POST /api/v1/vision/bill/read` | multipart: `file` (jpg/png/webp/pdf…) + فرم `mode=read` | `VisionResponse` با `data` از نوع `BillData` |
| `POST /api/v1/vision/bill/analyze` | همان (پیش‌فرض `mode=analyze`) | داده + لایه دانش/تحلیل |
| `POST /api/v1/vision/ocr` | multipart: `file` | متن خام OCR |
| `POST /api/v1/vision/upload` | multipart: `file` | تشخیص خودکار نوع سند + استخراج |
| `POST /api/v1/vision/preprocess` | multipart: `file` | تصویر پیش‌پردازش‌شده |

```json
    "consumption_kwh": 265, "energy_charge": 4120000,
    "tax": 583200, "total_amount": 6415200,
    "line_items": [ { "description": "تبصره ۱۴", "amount": 1300000 } ],

```

**نمونه فراخوانی مستقیم برای تست:**

```bash
curl -s -X POST http://localhost:8003/api/v1/vision/bill/read \
  -F "file=@sample-bill.jpg" -F "mode=read" | jq
```

### ۵.۲ ⚠️ باگ شناسایی‌شده در مسیر فراخوانی

- کد فعلی ربات (`services/bill-bot/src/vision-client.ts`): ‏`POST {baseUrl}/vision/bill/read`
- مسیر واقعی سرویس: ‏`POST {baseUrl}/api/v1/vision/bill/read`
- اثر: درخواست 404 می‌شود و `readBillViaVision` مقدار null برمی‌گرداند → همیشه fallback (ورود دستی) فعال می‌شود.
- **اقدام:** اصلاح آدرس در `vision-client.ts` (و تصحیح سند ۰۳) پیش از هر تست میدانی.

### ۵.۳ سایر سرویس‌های Xennic (برای فازهای بعد)

| سرویس | مسیر/پورت | نقش در نقشه راه |

## ۶. معماری پیشنهادی MVP

```
 تلگرام (api.telegram.org)          بله (tapi.bale.ai)
        │ getUpdates/sendX                  │
        ▼                                  ▼
 ┌──────────────────────────────────────────────┐
 │   آداپتور پلتفرم (BotApi — یک کد، دو baseUrl) │
 └──────────────────┬───────────────────────────┘
                    ▼
 ┌──────────────────────────────────────────────┐
 │   هسته ربات (flow.ts — ماشین حالت، نشست‌های  │
 │   فقط-در-حافظه، بدون store)                  │
 └───┬──────────────────────────┬───────────────┘
     ▼                          ▼
 ┌──────────────┐        ┌───────────────────┐
 │ vision-client│        │ bill/extract.ts   │
 │ POST /api/v1 │        │ (fallback regex   │
 │ /vision/bill │        │  + اطمینان فیلد)   │
 │ /read        │        └───────────────────┘
 └──────┬───────┘
        ▼
 ┌──────────────────────────────┐
 │   نگاشت + ادغام → BillData   │
 │   → جدول چت (فرمت HTML/ساده) │   ← خروجی نهایی MVP (بدون ذخیره)
 └──────────────────────────────┘
```

اصول ثابت (مطابق سند ۰۱–۰۸):
- **دقت مقدم بر سرعت:** فیلد کم‌اطمینان با ⚠️ و دکمه/قالب «اصلاح» (ورود دستی همان فیلد) — بدون حدس عدد قطعی.
- **فارسی‌اول:** همه پیام‌ها و جدول RTL با اعداد فارسی (`faNumber`).
- **fallback همیشه:** خطای vision-service → مسیر محلی → پیام راهنمای خوانا نبودن (هرگز کرش).
- **بدون وابستگی سنگین:** اجرا با Node ≥ 22 و بدون build.

| | گزینه A — برش اسکلت موجود (پیشنهادی) | گزینه B — MVP مستقل از صفر | گزینه C — ادامه مسیر کامل اسکلت |

| مزیت | سریع‌ترین مسیر به MVP؛ بهره از کد تست‌شده؛ مسیر رشد روشن به فازهای بعد | کنترل کامل، سطح کد حداقلی | محصول کامل طبق سند ۰۹ |

## ۸. نقشه راه پیشنهادی

### فاز ۰ — MVP «جدول فقط، بدون ذخیره» (پیشنهاد: ۱ تا ۲ روز کاری)

| # | کار | معیار پذیرش |
| --- | --- | --- |
| 1 | اصلاح باگ مسیر vision در `vision-client.ts` (+ تصحیح سند ۰۳) | فراخوانی مستقیم curl به همان مسیر پاسخ 200 می‌دهد |
| 2 | غیرفعال‌سازی store در startup؛ حذف دکمه‌های PDF/مشاوره/تحلیل از جریان؛ حذف `/status`، `/requests` | `DATA_DIR` ساخته نمی‌شود؛ هیچ فایل‌نویسی در اجرا |
| 3 | افزودن env `BILL_BOT_MODE=mvp\|full` (یا معادل) برای برش دامنه | جابه‌جایی حالت بدون تغییر کد |
| 4 | نصب توکن‌های واقعی (BotFather / آیدی‌بات بله) در env | `getMe` هر دو سکو موفق |
| 5 | راه‌اندازی vision-service و تست ۱۰ قبض واقعی (عکس + PDF) | ≥ ۹۰٪ فیلدهای کلیدی بدون ورود دستی (معیار G2) |
| 6 | تست میدانی با ۵ کاربر | جدول صحیح، fallback درست، بدون باگ در long-polling |
| 7 | ثبت نتایج و تصمیم برای فاز ۱ | گزارش تست + لیست شکاف‌های OCR |

### فاز ۱ — اتصال کامل به Xennic (پیشنهاد: ۲ تا ۳ روز)

- کالیبراسیون OCR/استخراج در vision-service با ۲۰ قبض واقعی (زیرنویس، چرخش، انواع قبوض).
- تکمیل نگاشت `VisionResponse.data` ↔ `BillData` (شناسه قبض/پرداخت، دوره، منطقه، سه‌زمانه).
- اتصال به `apps/api` برای احراز هویت workspace و ثبت رویدادها (در صورت نیاز).
- افزودن متریک‌های پایه (تعداد قبض، موفقیت OCR، fallback) و لاگ بدون PII.

### فاز ۲ — برگشت قابلیت‌های مستند (پس از تأیید کارفرما)

- فعال‌سازی تحلیل تعرفه ۱۴۰۵ (کد آماده) ← مقایسه مبلغ محاسبه‌شده با قبض (انحراف ≤ ۵٪).
- گزارش PDF فارسی (فونت وزیرمتن) و مسیر مشاوره (PV/تلفن) با ذخیره‌سازی مطابق سند ۰۸ (AES، پاک‌سازی ۲۴ ساعته، /delete).
- اتصال ai-service برای روایت هوشمند (اختیاری).
- استقرار Docker/PM2 و پایش.

> تذکر حاکمیتی: طبق `docs/governance/`، توسعه روی شاخه‌ی جدا از `dev` انجام و پس از تأیید از طریق PR به `dev` (و سپس Release Gate به `main`) منتقل می‌شود. جلسه‌ی جاری روی شاخه `arena/01a0296d-xennic` (منشعب از `dev@8effe1a`) انجام می‌شود.
