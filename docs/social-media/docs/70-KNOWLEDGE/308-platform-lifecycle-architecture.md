## ۱. Purpose

KNW-305 معماری چرخه حیات پلتفرم سازمانی SMOS است. این سند SSOT (تک منبع حقیقت) برای **تعریف وضعیت‌ها، انتقال‌ها، نسخه‌بندی، انتشار، مدیریت تغییر، تکامل پیکربندی، بازنشستگی و اعتبارسنجی چرخه حیات** برای همه موجودیت‌های پلتفرمی تعریف‌شده در KNW-301، KNW-302، KNW-303 و KNW-304 است.

### چرا KNW-305 وجود دارد

بدون یک معماری چرخه حیات پلتفرمی:

- وضعیت موجودیت‌های پلتفرمی بدون ساختار و ضمنی باقی می‌ماند
- انتقال بین وضعیت‌ها بدون معیار و تأیید انجام می‌شود
- نسخه‌بندی موجودیت‌ها یکپارچه و قابل ردیابی نیست
- انتشار نسخه‌های جدید بدون چارچوب رسمی انجام می‌شود
- بازنشستگی و بایگانی موجودیت‌ها بدون فرآیند مشخصی صورت می‌گیرد
- ردیابی تغییرات در طول چرخه حیات برای Agentها و مصرف‌کنندگان امکان‌پذیر نیست

KNW-305 این مشکلات را با تعریف **مدل رسمی چرخه حیات پلتفرم** حل می‌کند.

## ۴. Lifecycle Philosophy

### فلسفه چرخه حیات پلتفرمی

SMOS چرخه حیات پلتفرمی را به عنوان **سفر موجودیت از ایده تا بازنشستگی** در معماری پلتفرم می‌بیند که:

1. **مستقل از پلتفرم است** — همه موجودیت‌های پلتفرمی از یک مدل چرخه حیات واحد پیروی می‌کنند
2. **غیرخطی است** — موجودیت می‌تواند به وضعیت‌های قبلی بازگردد
3. **قابل پیش‌بینی است** — وضعیت فعلی و انتقال‌های ممکن برای همه شفاف است
4. **مبتنی بر ارزش است** — موجودیت تا زمانی که ارزش ایجاد می‌کند فعال می‌ماند
5. **مسئولانه است** — بازنشستگی و بایگانی با اطلاع مصرف‌کنندگان انجام می‌شود

### اصول هستی‌شناسی چرخه حیات

| اصل                                   | توضیح                                        |
| ------------------------------------- | -------------------------------------------- |
| **هر موجودیت یک وضعیت دارد**          | وضعیت موجودیت تعیین‌کننده قابلیت مصرف آن است |
| **هر انتقال یک رویداد دارد**          | تغییر وضعیت توسط یک رویداد مشخص فعال می‌شود  |
| **هر نسخه یک تاریخ دارد**             | همه نسخه‌ها دارای برچسب زمانی هستند          |
| **هر بازنشستگی یک جایگزین دارد**      | موجودیت بازنشسته‌شده باید جایگزین معرفی کند  |
| **چرخه حیات مستقل از پیاده‌سازی است** | مدل چرخه حیات برای همه پلتفرم‌ها یکسان است   |

## ۸. State Transition Model

### مدل انتقال وضعیت

انتقال وضعیت‌ها بر اساس **گراف انتقال مجاز** انجام می‌شود.

### انتقال‌های مجاز

| از                    | به                    | رویداد               | نیاز به تأیید | مسئول تأیید  |
| --------------------- | --------------------- | -------------------- | ------------- | ------------ |
| STATE-01 (Draft)      | STATE-02 (Review)     | بررسی تکمیل پیش‌نویس | خیر           | تولیدکننده   |
| STATE-02 (Review)     | STATE-03 (Approved)   | تأیید نهایی بازبینی  | بله           | متولی        |
| STATE-02 (Review)     | STATE-01 (Draft)      | نیاز به اصلاحات      | خیر           | بازبین       |
| STATE-03 (Approved)   | STATE-04 (Active)     | فعال‌سازی            | بله           | مالک         |
| STATE-03 (Approved)   | STATE-01 (Draft)      | تغییر نیازمندی‌ها    | بله           | معمار        |
| STATE-04 (Active)     | STATE-05 (Maintained) | تشخیص نیاز به تغییر  | خیر           | متولی        |
| STATE-05 (Maintained) | STATE-01 (Draft)      | شروع تغییر           | بله           | معمار        |
| STATE-05 (Maintained) | STATE-04 (Active)     | تکمیل تغییر          | بله           | مالک         |
| STATE-04 (Active)     | STATE-06 (Deprecated) | تصمیم به بازنشستگی   | بله           | مالک + معمار |
| STATE-05 (Maintained) | STATE-06 (Deprecated) | تصمیم به بازنشستگی   | بله           | مالک + معمار |
| STATE-06 (Deprecated) | STATE-07 (Retired)    | پایان مهلت انقضا     | بله           | معمار دانش   |
| STATE-06 (Deprecated) | STATE-04 (Active)     | لغو بازنشستگی        | بله           | معمار دانش   |
| STATE-07 (Retired)    | STATE-08 (Archived)   | بایگانی نهایی        | بله           | معمار دانش   |
| STATE-07 (Retired)    | STATE-04 (Active)     | بازگردانی اضطراری    | بله           | معمار دانش   |
| STATE-08 (Archived)   | STATE-07 (Retired)    | بازیابی از بایگانی   | بله           | معمار دانش   |

### قواعد انتقال

| قاعده  | توضیح                                                                       |
| ------ | --------------------------------------------------------------------------- |
| TRN-01 | انتقال فقط در مسیرهای مجاز (گراف بالا) مجاز است                             |
| TRN-02 | انتقال نیازمند ثبت در رجیستری چرخه حیات است                                 |
| TRN-03 | انتقال‌های قطعی (STATE-07 ← STATE-08) غیرقابل بازگشت هستند مگر با تأیید A-4 |
| TRN-04 | انتقال STATE-04 → STATE-06 نیازمند اطلاع همه مصرف‌کنندگان است               |
| TRN-05 | انتقال STATE-01 → STATE-04 مستقیم مجاز نیست                                 |

## ۱۰. Versioning Strategy

### استراتژی نسخه‌بندی

همه موجودیت‌های پلتفرمی از **مدل نسخه‌بندی معنایی (SemVer)** پیروی می‌کنند.

### ساختار نسخه

```
MAJOR.MINOR.PATCH-status+build
```

| بخش    | توضیح                                         | مثال            |
