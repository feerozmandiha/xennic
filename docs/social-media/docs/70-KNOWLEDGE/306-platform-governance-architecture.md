## ۱. Purpose

KNW-304 معماری حکمرانی پلتفرم سازمانی SMOS است. این سند SSOT (تک منبع حقیقت) برای **تعریف اصول، اختیارات، مالکیت، انطباق، اعتبارسنجی، سلسله‌مراتب تأیید و مسئولیت‌پذیری معماری** برای همه موجودیت‌های پلتفرمی تعریف‌شده در KNW-301، KNW-302 و KNW-303 است.

### چرا KNW-304 وجود دارد

بدون یک معماری حکمرانی پلتفرمی:

- تصمیم‌گیری درباره موجودیت‌های پلتفرمی بدون چارچوب و پراکنده انجام می‌شود
- مالکیت و مسئولیت موجودیت‌های پلتفرمی مبهم باقی می‌ماند
- انطباق با قواعد کسب‌وکار (KNW-102) در سطح پلتفرم قابل تضمین نیست
- اعتبارسنجی تغییرات در موجودیت‌های پلتفرمی بدون معیار مشخص انجام می‌شود
- استثناها و انحرافات از معماری بدون فرآیند رسمی مدیریت می‌شوند
- حساب‌پذیری معماری در سطح سازمانی قابل ردیابی نیست

KNW-304 این مشکلات را با تعریف **چارچوب رسمی حکمرانی پلتفرم** حل می‌کند.

| سند         | نقش                                                      |

## ۴. Governance Philosophy

### فلسفه حکمرانی پلتفرمی

SMOS حکمرانی پلتفرمی را به عنوان **چارچوب تصمیم‌گیری مسئولانه** در معماری پلتفرم می‌بیند که:

1. **توانمندساز است** — نه محدودکننده. حکمرانی مسیر را مشخص می‌کند نه مانع را
2. **مبتنی بر ریسک است** — سطح حکمرانی با سطح ریسک تصمیم متناسب است
3. **شفاف است** — همه قواعد، اختیارات و مسئولیت‌ها مستند و قابل دسترس هستند
4. **قابل اندازه‌گیری است** — اثربخشی حکمرانی با شاخص‌های مشخص ارزیابی می‌شود
5. **تکامل‌پذیر است** — چارچوب حکمرانی در طول زمان بر اساس یادگیری سازمانی بهبود می‌یابد

### اصول هستی‌شناسی حکمرانی

| اصل                                 | توضیح                                                 |
| ----------------------------------- | ----------------------------------------------------- |
| **هر تصمیم یک سطح اختیار دارد**     | تصمیمات در سطوح A-0 تا A-4 طبقه‌بندی می‌شوند          |
| **هر موجودیت یک مالک دارد**         | هر موجودیت پلتفرمی یک مالک مشخص دارد                  |
| **هر قاعده یک منبع دارد**           | قواعد حکمرانی از KNW-102 یا KNW-304 مشتق می‌شوند      |
| **هر استثنا یک انقضا دارد**         | استثناها موقت هستند و پس از انقضا نیاز به تمدید دارند |
| **حکمرانی مستقل از پیاده‌سازی است** | چارچوب حکمرانی برای همه پلتفرم‌ها یکسان است           |

## ۹. Ownership Model

### مدل مالکیت پلتفرمی

هر موجودیت پلتفرمی دارای یک **مالک (Owner)** و یک **متولی (Steward)** است.

| نقش                   | مسئولیت                                  | سطح اختیار |
| --------------------- | ---------------------------------------- | ---------- |
| مالک (Owner)          | تصمیم‌گیری نهایی درباره موجودیت          | A-3 یا A-4 |
| متولی (Steward)       | نگهداری و به‌روزرسانی روزانه موجودیت     | A-2        |
| تولیدکننده (Producer) | ایجاد و مستندسازی موجودیت                | A-1 یا A-2 |
| مصرف‌کننده (Consumer) | استفاده از موجودیت در تصمیمات و فرآیندها | A-0        |

### مالکیت موجودیت‌های پلتفرمی

| موجودیت                         | مالک پیش‌فرض      | متولی پیش‌فرض |
| ------------------------------- | ----------------- | ------------- |
| PLTD-\* (دامنه‌ها)              | استراتژیست پلتفرم | معمار پلتفرم  |
| LYR-PLT-\* (لایه‌ها)            | معمار پلتفرم      | مهندس پلتفرم  |
| PLTCAP-\* (قابلیت‌ها)           | مدیر قابلیت       | معمار قابلیت  |
| CAP-PLT-\* (قابلیت‌های اختصاصی) | مدیر قابلیت       | معمار قابلیت  |
| SRV-PLT-\* (سرویس‌ها)           | مدیر سرویس        | مهندس سرویس   |
| PLTC-\* (مؤلفه‌ها)              | معمار فنی         | مهندس سیستم   |
| PLTM-\* (ماژول‌ها)              | مدیر ماژول        | مالک فرآیند   |
| RL-\* (روابط)                   | معمار رابطه       | متولی دانش    |

## ۱۰. Accountability Model

### مدل حساب‌پذیری

| اصل                    | توضیح                                       |
| ---------------------- | ------------------------------------------- |
| **تک مسئول**           | هر تصمیم و تغییر یک مسئول نهایی دارد        |

## ۲۴. Governance Evolution

### تکامل حکمرانی

چارچوب حکمرانی پلتفرمی یک **سند زنده** است که در طول زمان تکامل می‌یابد.

### اصول تکامل

| اصل    | توضیح                                                            |
| ------ | ---------------------------------------------------------------- |
| EVO-01 | تغییر در چارچوب حکمرانی نیاز به ADR (معماری ثبت تصمیم) دارد      |
| EVO-02 | هر تغییر باید در Change Log (بخش ۳۰) ثبت شود                     |
| EVO-03 | تغییرات باید با مصرف‌کنندگان (AI-_, AUT-_) اطلاع‌رسانی شود       |
| EVO-04 | بازبینی دوره‌ای چارچوب حداقل هر ۶ ماه یکبار                      |
| EVO-05 | بازخورد از Agentها و مصرف‌کنندگان در بهبود چارچوب استفاده می‌شود |

### مسیر تکامل پیشنهادی

| فاز          | تمرکز                       | بهبودها                               |
| ------------ | --------------------------- | ------------------------------------- |
| v1.x (کنونی) | چارچوب پایه حکمرانی پلتفرمی | اصول, اختیار, مالکیت, انطباق          |
| v2.x         | حکمرانی خودکار              | قواعد قابل اجرا توسط Agentها          |
| v3.x         | حکمرانی تطبیقی              | تنظیم خودکار سطح حکمرانی بر اساس ریسک |
