## ۱. معرفی

این سند **سیستم ثبت تصمیمات معماری (ADR)** را برای SMOS تعریف می‌کند.
تصمیمات معماری آینده باید توسط ADR مدیریت شوند.

## ۲. اصول ADR

| اصل    | توضیح                                      |
| ------ | ------------------------------------------ |
| ADR-01 | هر تصمیم معماری باید در ADR ثبت شود        |
| ADR-02 | ADRها غیرقابل حذف هستند (فقط supersede)    |
| ADR-03 | هر ADR باید گزینه‌های جایگزین را بررسی کند |
| ADR-04 | هر ADR باید دلیل انتخاب را توضیح دهد       |
| ADR-05 | ADRها برای انسان و Agent قابل خواندن هستند |

## ۴. چرخه حیات ADR

```
Proposed (پیشنهادی)
  │  [نویسنده: هر کس]
  ▼
Draft (پیش‌نویس)
  │  [تکمیل توسط نویسنده]
  ▼
Review (بازبینی) ← ۱ هفته
  │  [بازبین: معمار سیستم]
  ├── Approved (تأیید)
  │    └── Active (فعال) ← ۶ ماه
  │         ├── Active (تمدید)
  │         └── Superseded (جایگزین)
  │              └── ADR جدید
  └── Rejected (رد)
       └── Close (بسته)
```

### وضعیت‌های ADR

| وضعیت        | توضیح                       |
| ------------ | --------------------------- |
| `proposed`   | ایده اولیه                  |
| `draft`      | پیش‌نویس در حال تکمیل       |
| `review`     | در حال بازبینی              |
| `approved`   | تأیید شده، منتظر فعال‌سازی  |
| `active`     | فعال و اجرایی               |
| `superseded` | جایگزین شده توسط ADR جدیدتر |
| `rejected`   | رد شده                      |
| `closed`     | بسته شده (برای rejected)    |

## ۵. فرایند تأیید ADR

| مرحله              | مسئول                  | حداکثر زمان |
| ------------------ | ---------------------- | ----------- |
| **پیشنهاد**        | هر کس (انسان یا Agent) | —           |
| **ثبت شماره**      | معمار سیستم            | ۲۴ ساعت     |
| **تکمیل پیش‌نویس** | نویسنده                | ۱ هفته      |
| **بازبینی**        | معمار سیستم            | ۱ هفته      |
| **تأیید**          | سطح مجاز               | ۱ هفته      |
| **اعلام**          | معمار سیستم            | ۲۴ ساعت     |

### سطوح تأیید ADR

| نوع ADR                      | Approver         |
| ---------------------------- | ---------------- |
| معماری (Architectural)       | معمار سیستم      |
| استراتژیک (Strategic)        | مدیر ارشد        |
| قانون اساسی (Constitutional) | مدیر ارشد + هیئت |
| عملیاتی (Operational)        | معمار سیستم      |
| فنی (Technical)              | مهندس ارشد       |

## ۶. رابطه ADR با قانون اساسی و معماری

```
CON-000  قانون اساسی
  │  ← ADRها نمی‌توانند CON-000 را نقض کنند
  ▼
ARCH-*  اسناد معماری
  │  ← ADRها به ARCH-* ارجاع می‌دهند
  ▼
ADR-NNN  تصمیمات معماری
  │  ← ADRها پیاده‌سازی می‌کنند
  ▼
Implementation  پیاده‌سازی
```

### قواعد

1. ADRها **تابع** CON-000 هستند
2. ADRها به ARCH-\* ارجاع می‌دهند (نمی‌نویسند)
3. ADRها **جایگزین** بخش‌های خاصی از معماری می‌شوند
4. ADR `superseded` به ADR جدیدتر لینک می‌دهد
5. ADRها اسناد زنده (living) نیستند — فقط تصمیمات را ثبت می‌کنند

---

## ۷. قواعد Superseding

| شرط                    | نتیجه                             |
| ---------------------- | --------------------------------- |
| ADR-A خطا دارد         | ADR-B جایگزین ADR-A               |
| شرایط تغییر کرده       | ADR-C جایگزین ADR-A               |
| تصمیم بهینه‌تر یافت شد | ADR-D جایگزین ADR-A               |
| CON-000 تغییر کرد      | ADRهای مغایر بررسی و جایگزین شوند |

هر ADR `superseded` باید به ADR جایگزین لینک داشته باشد.

## ۸. قالب ADR (ADR Template)

```markdown
# ADR-NNN: عنوان تصمیم

> **وضعیت:** proposed | draft | review | approved | active | superseded | rejected
> **تاریخ:** YYYY-MM-DD
> **نویسنده:** نام
> **مشتری:** (دپارتمان یا تیم)

## زمینه (Context)

چه مسئله‌ای باعث این تصمیم شد؟

## گزینه‌ها (Options)

گزینه‌های بررسی‌شده:

1. گزینه A — مزایا و معایب
2. گزینه B — مزایا و معایب
3. گزینه C — مزایا و معایب

## تصمیم (Decision)

گزینه انتخاب‌شده و دلیل.

## پیامدها (Consequences)

تأثیر این تصمیم بر سایر اجزا.

## الزامات (Requirements)

چه چیزهایی برای اجرا نیاز است؟

## ارجاعات (References)

- CON-000
- ARCH-\*
- ADR-\*

---

## تغییرات

| ---- | ---------- | ------------ | ------- |
| ۱.۰  | YYYY-MM-DD | انتشار اولیه | نویسنده |
```
