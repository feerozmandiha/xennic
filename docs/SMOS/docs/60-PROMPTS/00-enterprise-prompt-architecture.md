## ۱. Executive Summary

PRM-000 سند مادر معماری پرامپت سازمانی SMOS است. تمام PRM-001 تا PRM-999 و هر پرامپت در SMOS صرفاً از این سند مشتق می‌شوند.

این سند **فقط معماری پرامپت** را تعریف می‌کند — نه خود پرامپت‌ها، نه کد، نه API، نه workflow، نه ابزار. معماری مستقل از هر مدل زبانی، فروشنده، پلتفرم ابری، چارچوب پرامپت‌نویسی یا API است و برای حداقل ۱۰ سال اعتبار دارد.

### هسته معماری

SMOS از **خانواده‌ای از پرامپت‌های استاندارد** تشکیل شده است که هر کدام یک هدف معماری مشخص دارند. پرامپت‌ها از طریق **ترکیب** با هم کار می‌کنند، نه تکرار. Registry مرکزی همه پرامپت‌ها را مدیریت می‌کند، اما هر پرامپت در مرز هویت خود مستقل تعریف می‌شود.

PRM-000 معماری را تعریف می‌کند — PRM-001 نمایه را نگه می‌دارد — PRM-NNN پیاده‌سازی می‌کند.

## ۲. Purpose

### هستی‌شناسی سند

PRM-000 به‌عنوان **منبع حقیقت واحد (SSOT)** برای تمام جنبه‌های معماری پرامپت در SMOS وجود دارد. این سند تعریف می‌کند:

- **یک پرامپت در SMOS چیست** — هستی‌شناسی پرامپت سازمانی
- **چگونه پرامپت‌ها ساخته می‌شوند** — الگوی معماری برای ایجاد پرامپت جدید
- **چگونه پرامپت‌ها با هم کار می‌کنند** — مدل ترکیب و زنجیره پرامپت
- **مرزهای پرامپت** — هویت، متغیر، بافت، وابستگی
- **چرخه حیات پرامپت** — از طراحی تا بازنشستگی

### جایگاه در سلسله‌مراتب اسناد

```
CON-000  (قانون اساسی — اصول عالی)
  │
ARCH-*   (معماری سیستم — ساختار)
  │
AI-000   (معماری Agentها — عامل‌ها)
  │
PRM-000  ← این سند (معماری پرامپت — الگو)
  │
PRM-001   (نمایه پرامپت — ثبت مرکزی تمام پرامپت‌ها)
PRM-NNN   (مشخصات پرامپت اختصاصی)
  │
AUT-*    (Workflowهایی که از پرامپت استفاده می‌کنند)
```

### آنچه PRM-000 مالک است

PRM-000 تنها مالک موارد زیر است — هر چیز دیگر در اسناد بالادست باقی می‌ماند:

- ✅ معماری پرامپت (ساختار، لایه‌ها، روابط)
- ✅ هستی‌شناسی پرامپت (تعریف، انواع، هویت)
- ✅ مدل ترکیب پرامپت (Composition)
- ✅ مدل بافت پرامپت (Context)
- ✅ مدل متغیر پرامپت (Variables)
- ✅ مدل وابستگی پرامپت (Dependencies)
- ✅ چرخه حیات پرامپت
- ✅ مدل حاکمیت پرامپت
- ✅ چارچوب اعتبارسنجی و کیفیت
- ✅ مدل امنیت و حسابرسی
- ✅ Registry مرکزی
- ✅ بلوک‌های ماشین‌خوان

## ۵. Design Principles

| ID        | اصل                         | توضیح                                                                                               |
| --------- | --------------------------- | --------------------------------------------------------------------------------------------------- |
| **PP-01** | **Separation of Concerns**  | هر پرامپت یک مسئولیت واحد دارد — پرامپت استراتژیک با عملیاتی ترکیب نمی‌شود                          |
| **PP-02** | **Composable by Design**    | پرامپت‌ها برای ترکیب (Composition) طراحی می‌شوند — پرامپت‌های بزرگ از پرامپت‌های کوچک ساخته می‌شوند |
| **PP-03** | **Context Isolation**       | هر پرامپت بافت (Context) خود را مشخصاً تعریف می‌کند — بافت خارجی تزریق می‌شود نه پیش‌فرض            |
| **PP-04** | **Deterministic Variables** | متغیرها دارای نوع، دامنه و اعتبارسنجی مشخص هستند — متغیر آزاد ممنوع                                 |
| **PP-05** | **Version Integrity**       | هر پرامپت دارای نسخه معنایی (SemVer) است — وابستگی به نسخه دقیق                                     |
| **PP-06** | **Explicit Dependencies**   | وابستگی پرامپت‌ها صریح و قابل ردیابی است — وابستگی ضمنی ممنوع                                       |
| **PP-07** | **Governance by Design**    | هر پرامپت دارای سطح اختیار، نقش مالک و مجوز دسترسی مشخص است                                         |
| **PP-08** | **Audit Traceability**      | هر پرامپت قابل ردیابی به منبع، تغییر و مصرف‌کننده است                                               |
| **PP-09** | **Model Agnostic**          | پرامپت‌ها مستقل از ساختار System/User/Assistant و قواعد خاص هر LLM هستند                            |
| **PP-10** | **Vendor Neutral**          | پرامپت‌ها به Vendor یا API خاصی وابسته نیستند                                                       |
| **PP-11** | **Fail Gracefully**         | خطا در یک پرامپت زنجیره را نمی‌شکند — Fallback تعریف می‌شود                                         |
| **PP-12** | **Discoverable Registry**   | همه پرامپت‌ها در Registry مرکزی قابل کشف هستند                                                      |

## ۷. Prompt Identity Model

### شناسه پرامپت

هر پرامپت در SMOS دارای یک شناسه یکتای جهانی است:

```
PRM-NNN[-NNN]
```

| بخش           | توضیح                                     | مثال          |
| ------------- | ----------------------------------------- | ------------- |
| **PRM**       | Prefix ثابت همه پرامپت‌ها                 | PRM           |
| **NNN** (اول) | شماره خانواده + شماره ترتیبی              | 001, 201, 901 |
| **NNN** (دوم) | شماره نسخه پرامپت در یک خانواده (اختیاری) | 001           |

**مثال‌ها:**

- `PRM-001` — نمایه پرامپت (Registry)
- `PRM-101` — پرامپت استراتژی محتوا (خانواده STR)
- `PRM-201` — پرامپت تولید محتوا (خانواده CON)
- `PRM-901-001` — پرامپت Orchestration (خانواده SYS)

### فراداده اجباری هر پرامپت

| فیلد           | نوع    | اجباری | توضیح                                                |
| -------------- | ------ | ------ | ---------------------------------------------------- |
| `id`           | string | yes    | شناسه یکتا (PRM-NNN)                                 |
| `name`         | string | yes    | نام کوتاه                                            |
| `description`  | string | yes    | توضیح                                                |
| `family`       | enum   | yes    | FAM-STR, FAM-CON, FAM-OPS, FAM-KNW, FAM-SYS          |
| `type`         | enum   | yes    | PT-01 تا PT-07                                       |
| `complexity`   | enum   | yes    | C-0 تا C-4                                           |
| `authority`    | enum   | yes    | A-0 تا A-4                                           |
| `owner`        | string | yes    | نقش یا شخص مسئول                                     |
| `version`      | semver | yes    | Semantic Version                                     |
| `status`       | enum   | yes    | draft, review, approved, active, deprecated, retired |

| `consumers`    | array  | no     | مصرف‌کنندگان (Agent, Workflow)                       |

## ۸. Prompt Lifecycle

### فازهای چرخه حیات

| فاز            | شناسه  | توضیح                                               |
| -------------- | ------ | --------------------------------------------------- |
| **Idea**       | LIF-01 | ایده اولیه — نیاز به ثبت در ADR برای معماری جدید    |
| **Design**     | LIF-02 | طراحی معماری پرامپت — ساختار، هویت، مرز             |
| **Draft**      | LIF-03 | نگارش اولیه — تعریف متغیرها، بافت، وابستگی          |
| **Review**     | LIF-04 | بازبینی معماری و ساختار — تأیید انطباق با PRM-000   |
| **Approved**   | LIF-05 | تأیید نهایی — ثبت در Registry                       |
| **Active**     | LIF-06 | فعال در محیط تولید — قابل استفاده توسط مصرف‌کنندگان |
| **Deprecated** | LIF-07 | اعلام منسوخ‌شدن — حداقل ۳۰ روز اطلاع قبل از حذف     |
| **Retired**    | LIF-08 | حذف کامل — پس از اطمینان از عدم استفاده             |

### قواعد Lifecycle

| ID      | قاعده                                                               |
| ------- | ------------------------------------------------------------------- |
| LIF-R01 | هیچ پرامپت بدون شناسه ثبت‌شده در PRM-001 Active نمی‌شود             |
| LIF-R02 | تغییر در خانواده، نوع یا سطح اختیار نیازمند ADR است                 |
| LIF-R03 | Deprecation باید در PRM-001 ثبت و به مصرف‌کنندگان اعلام شود         |
| LIF-R04 | هر پرامپت در هر لحظه دقیقاً یک فاز Lifecycle دارد                   |
| LIF-R05 | پرامپت Deprecated حداقل ۳۰ روز پس از اعلام به Retirement می‌رود     |
| LIF-R06 | Retirement تنها پس از تأیید عدم مصرف توسط مصرف‌کنندگان انجام می‌شود |

## ۹. Prompt Composition Model

### الگوهای ترکیب

SMOS دارای ۴ الگوی ترکیب پرامپت است:

| الگو            | شناسه | توضیح                                               | مثال                          |
| --------------- | ----- | --------------------------------------------------- | ----------------------------- |
| **Sequential**  | CP-01 | پرامپت‌ها به صورت پشت‌سر هم اجرا می‌شوند            | تولید → بازبینی → اصلاح       |
| **Nested**      | CP-02 | یک پرامپت درون پرامپت دیگر جاسازی می‌شود            | پرامپت دانش درون پرامپت تولید |
| **Parallel**    | CP-03 | چند پرامپت همزمان اجرا می‌شوند و نتایج تجمیع می‌شود | تحلیل همزمان چند کانال        |
| **Conditional** | CP-04 | انتخاب مسیر بر اساس خروجی پرامپت قبلی               | مسیر تأیید خودکار یا انسانی   |

### قواعد ترکیب

| ID     | قاعده                                                                          |
| ------ | ------------------------------------------------------------------------------ |
| CP-R01 | پرامپت والد هیچ‌گاه متغیرهای پرامپت فرزند را نادیده نمی‌گیرد                   |
| CP-R02 | هر پرامپت در زنجیره بافت (Context) خود را از پرامپت بالادست دریافت می‌کند      |
| CP-R03 | خطا در یک پرامپت فرزند به پرامپت والد منتشر می‌شود مگر Fallback تعریف شده باشد |
| CP-R04 | پرامپت‌های Parallel باید خروجی قابل تجمیع داشته باشند                          |
| CP-R05 | Depth ترکیب پرامپت‌های Nested حداکثر ۳ سطح است                                 |

### مدل Dependency Graph

وابستگی بین پرامپت‌ها یک **گراف غیرمدور جهت‌دار (DAG)** است:

```
PRM-101 (Content Strategy)
   │
   ▼
PRM-201 (Content Production)
   │
   ├──► PRM-202 (Content Review)
   │        │
   │        ▼
   │     PRM-203 (Content Refinement)
   │
   └──► PRM-301 (Publishing Format)
```

## ۱۳. Prompt Versioning

### نسخه‌بندی معنایی (SemVer)

PRM-000 از نسخه‌بندی Semantic Versioning 2.0.0 پیروی می‌کند:

```
MAJOR.MINOR.PATCH
```

| بخش       | تغییر                             | مثال                       |
| --------- | --------------------------------- | -------------------------- |
| **MAJOR** | تغییرات ناسازگار با نسخه‌های قبلی | تغییر در متغیرهای required |
| **MINOR** | افزودن قابلیت سازگار با عقب       | افزودن متغیر optional جدید |
| **PATCH** | رفع اشکال یا بهبود جزئی           | اصلاح دستورالعمل           |

### قواعد نسخه‌بندی

| ID      | قاعده                                                     |
| ------- | --------------------------------------------------------- |
| VER-R01 | همه پرامپت‌ها باید دارای نسخه SemVer باشند                |
| VER-R02 | MAJOR=0 نشان‌دهنده پیش‌نویس (unstable) است                |
| VER-R03 | پرامپت‌های Active باید MAJOR ≥ 1 داشته باشند              |
| VER-R04 | تغییر در family, type یا authority نیازمند MAJOR bump است |
| VER-R05 | افزودن متغیر required جدید نیازمند MAJOR bump است         |
| VER-R06 | هر نسخه باید در Change Log ثبت شود                        |

## ۱۸. Prompt Audit

### اصول حسابرسی

| اصل                           | توضیح                                           |
| ----------------------------- | ----------------------------------------------- |
| **هر پرامپت قابل ردیابی است** | همه تغییرات، مصرف‌کنندگان و نسخه‌ها ثبت می‌شوند |
| **هر تغییر ثبت می‌شود**       | Change Log برای همه پرامپت‌ها                   |
| **هر مصرف قابل پیگیری است**   | چه کسی، کِی، کدام نسخه را مصرف کرده             |
| **حسابرسی دوره‌ای**           | بازبینی فصلی همه پرامپت‌های Active              |

### رویدادهای حسابرسی

| رویداد                   | شناسه  | توضیح                              |
| ------------------------ | ------ | ---------------------------------- |
| **Prompt Created**       | AUD-01 | پرامپت جدید ایجاد شد               |
| **Prompt Updated**       | AUD-02 | نسخه جدید منتشر شد                 |
| **Prompt Deprecated**    | AUD-03 | پرامپت منسوخ اعلام شد              |
| **Prompt Retired**       | AUD-04 | پرامپت بازنشسته شد                 |
| **Prompt Consumed**      | AUD-05 | پرامپت توسط Agent/Workflow مصرف شد |
| **Prompt Access Denied** | AUD-06 | دسترسی غیرمجاز رد شد               |

### مدل مالکیت

| نقش                  | مسئولیت                                  | تعیین          |
| -------------------- | ---------------------------------------- | -------------- |

### قواعد مالکیت

| OWN-R01 | هر پرامپت دقیقاً یک Prompt Owner دارد            |

| OWN-R04 | تغییر Owner باید در ADR ثبت شود                  |

## ۲۰. Prompt Registry

### PRM-001 — نمایه مرکزی پرامپت

PRM-001 نمایه مرکزی همه پرامپت‌های SMOS است. هر پرامپت در SMOS باید در PRM-001 ثبت شود. PRM-001 شامل:

- فهرست کامل همه پرامپت‌ها با شناسه و وضعیت
- DAG وابستگی بین پرامپت‌ها
- مالک و مصرف‌کننده هر پرامپت
- نسخه جاری و تاریخ آخرین تغییر
- سطوح امنیتی و اختیار

### قواعد Registry

| ID      | قاعده                                                               |
| ------- | ------------------------------------------------------------------- |
| REG-R01 | همه پرامپت‌ها باید در PRM-001 ثبت شوند                              |
| REG-R02 | وضعیت پرامپت در Registry باید با وضعیت واقعی همخوانی داشته باشد     |
| REG-R03 | تغییر وضعیت باید ظرف ۲۴ ساعت در Registry منعکس شود                  |
| REG-R04 | Registry باید توسط ماشین (JSON) و انسان (Markdown) قابل خواندن باشد |

## ۲۱. Prompt Packaging

### بسته پرامپت (Prompt Package)

یک بسته پرامپت شامل:

| جزء                      | توضیح                      | اجباری |
| ------------------------ | -------------------------- | ------ |
| **Identity (PRM-NNN)**   | هویت و فراداده پرامپت      | yes    |
| **Context Definition**   | بافت مورد نیاز و منابع     | yes    |
| **Variable Definitions** | تعریف همه متغیرها          | yes    |
| **Dependency List**      | وابستگی‌ها                 | yes    |
| **Instruction Body**     | محتوای پرامپت (در PRM-NNN) | yes    |
| **Validation Rules**     | قواعد اعتبارسنجی اختصاصی   | no     |
| **Test Cases**           | موارد تست (اختیاری)        | no     |

### قواعد بسته‌بندی

| ID      | قاعده                                                    |
| ------- | -------------------------------------------------------- |
| PKG-R01 | هر بسته پرامپت باید شامل همه اجزای اجباری باشد           |
| PKG-R02 | بسته پرامپت باید با JSON Schema PRM-000 تطابق داشته باشد |
| PKG-R03 | بسته پرامپت باید دارای checksum (SHA-256) باشد           |

## ۲۴. Change Management

### انواع تغییر

| نوع             | شناسه  | توضیح                                         | نیازمند          |
| --------------- | ------ | --------------------------------------------- | ---------------- |
| **Patch**       | CHG-01 | رفع اشکال یا بهبود جزئی — backward compatible | Review           |
| **Minor**       | CHG-02 | افزودن قابلیت جدید — backward compatible      | Review + Owner   |
| **Major**       | CHG-03 | تغییر ناسازگار — نیاز به اطلاع مصرف‌کنندگان   | ADR + Architect  |
| **Deprecation** | CHG-04 | اعلام منسوخ‌شدن                               | Owner + Registry |
| **Retirement**  | CHG-05 | حذف کامل                                      | Owner + Auditor  |

### قواعد تغییر

| ID      | قاعده                                                            |
| ------- | ---------------------------------------------------------------- |
| CHG-R01 | همه تغییرات در Change Log پرامپت ثبت می‌شوند                     |
| CHG-R02 | تغییرات Major نیازمند اطلاع مصرف‌کنندگان ۳۰ روز قبل است          |
| CHG-R03 | تغییر در family, type یا authority نیازمند ADR است               |
| CHG-R04 | تغییرات باید backward compatible باشند (جز Major)                |
| CHG-R05 | تغییر در پرامپت‌های A-3 و A-4 نیازمند تأیید Prompt Architect است |

## ۲۵. Reading Guide

این سند توسط موجودیت‌های مختلف به روش‌های مختلف خوانده می‌شود:

### برای معمار سیستم

از **§۱ (Summary)** و **§۲ (Purpose)** و **§۴ (Prompt Architecture)** شروع کنید. سپس **§۵ (Design Principles)** و **§۶ (Prompt Taxonomy)** را بخوانید. **§۲۰ (Prompt Registry)** و **§۲۴ (Change Management)** برای مدیریت کلی اهمیت دارند.

### برای Prompt Engineer

از **§۷ (Prompt Identity Model)** , **§۹ (Prompt Composition Model)** , **§۱۰ (Prompt Context Model)** , **§۱۱ (Prompt Variable Model)** شروع کنید. **§۱۲ (Prompt Dependency Model)** و **§۱۳ (Prompt Versioning)** برای مدیریت وابستگی ضروری هستند. **§۲۲ (Machine Readable Blocks)** و **§۲۳ (JSON Schemas)** برای ایجاد پرامپت جدید الگو هستند.

### برای حکمران پرامپت

از **§۱۴ (Prompt Governance)** و **§۱۷ (Prompt Security)** و **§۱۸ (Prompt Audit)** شروع کنید. سپس **§۱۵ (Prompt Validation)** و **§۱۶ (Prompt Quality Model)** را بخوانید. **§۱۹ (Prompt Ownership)** مدل مالکیت را مشخص می‌کند.

### برای پیاده‌کننده Agent

از **§۹ (Composition Model)** و **§۱۰ (Context Model)** برای درک نحوه مصرف پرامپت شروع کنید. **§۱۱ (Variable Model)** نحوه تزریق داده را مشخص می‌کند. **§۲۰ (Registry)** برای کشف پرامپت‌های موجود استفاده می‌شود.
