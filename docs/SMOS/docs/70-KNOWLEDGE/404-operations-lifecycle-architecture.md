## ۱. Purpose

KNW-403 معماری چرخه حیات عملیات سازمانی SMOS است. این سند SSOT (تک منبع حقیقت) برای **تعریف وضعیت‌ها، انتقال‌ها، نسخه‌بندی، انتشار، مدیریت تغییر، تکامل پیکربندی، بازنشستگی، بایگانی و بازیابی** برای همه موجودیت‌های عملیاتی تعریف‌شده در KNW-401 است.

### چرا KNW-403 وجود دارد

بدون یک معماری چرخه حیات عملیاتی:

- وضعیت موجودیت‌های عملیاتی بدون ساختار و ضمنی باقی می‌ماند
- انتقال بین وضعیت‌ها بدون معیار و تأیید انجام می‌شود
- نسخه‌بندی موجودیت‌های عملیاتی یکپارچه و قابل ردیابی نیست
- انتشار نسخه‌های جدید موجودیت‌های عملیاتی بدون چارچوب رسمی انجام می‌شود
- بازنشستگی و بایگانی موجودیت‌های عملیاتی بدون فرآیند مشخصی صورت می‌گیرد
- ردیابی تغییرات در طول چرخه حیات برای Agentها و مصرف‌کنندگان امکان‌پذیر نیست

KNW-403 این مشکلات را با تعریف **مدل رسمی چرخه حیات عملیات** حل می‌کند.

## ۴. Lifecycle Philosophy

### فلسفه چرخه حیات عملیاتی

SMOS چرخه حیات عملیاتی را به عنوان **سفر موجودیت عملیاتی از ایده تا بازنشستگی** در معماری عملیات می‌بیند که:

1. **مستقل از عملیات است** — همه موجودیت‌های عملیاتی از یک مدل چرخه حیات واحد پیروی می‌کنند
2. **غیرخطی است** — موجودیت عملیاتی می‌تواند به وضعیت‌های قبلی بازگردد
3. **قابل پیش‌بینی است** — وضعیت فعلی و انتقال‌های ممکن برای همه شفاف است
4. **مبتنی بر ارزش است** — موجودیت عملیاتی تا زمانی که ارزش ایجاد می‌کند فعال می‌ماند
5. **مسئولانه است** — بازنشستگی و بایگانی موجودیت عملیاتی با اطلاع مصرف‌کنندگان انجام می‌شود
6. **هماهنگ با پلتفرم است** — چرخه حیات عملیات با چرخه حیات پلتفرم (KNW-305) هماهنگ است

### اصول هستی‌شناسی چرخه حیات

| اصل                                   | توضیح                                                |
| ------------------------------------- | ---------------------------------------------------- |
| **هر موجودیت یک وضعیت دارد**          | وضعیت موجودیت عملیاتی تعیین‌کننده قابلیت مصرف آن است |
| **هر انتقال یک رویداد دارد**          | تغییر وضعیت توسط یک رویداد مشخص فعال می‌شود          |
| **هر نسخه یک تاریخ دارد**             | همه نسخه‌های موجودیت عملیاتی دارای برچسب زمانی هستند |
| **هر بازنشستگی یک جایگزین دارد**      | موجودیت عملیاتی بازنشسته‌شده باید جایگزین معرفی کند  |
| **چرخه حیات مستقل از پیاده‌سازی است** | مدل چرخه حیات برای همه موجودیت‌های عملیاتی یکسان است |
| **چرخه حیات عملیات تابع حکمرانی است** | انتقال وضعیت تابع قواعد KNW-402 است                  |

## ۱۰. Versioning Strategy

### استراتژی نسخه‌بندی

همه موجودیت‌های عملیاتی از **مدل نسخه‌بندی معنایی (SemVer)** پیروی می‌کنند.

### ساختار نسخه

```
MAJOR.MINOR.PATCH-status+build
```

| بخش    | توضیح                                         | مثال            |
| ------ | --------------------------------------------- | --------------- |
| MAJOR  | تغییرات ناسازگار با نسخه‌های قبلی             | ۱.۰.۰ → ۲.۰.۰   |
| MINOR  | افزودن قابلیت جدید با سازگاری عقب‌گرد         | ۱.۰.۰ → ۱.۱.۰   |
| PATCH  | رفع باگ و بهبود بدون تغییر در ساختار          | ۱.۰.۰ → ۱.۰.۱   |
| status | وضعیت انتشار (draft, alpha, beta, rc, stable) | ۱.۰.۰-beta      |
| build  | شماره بیلد (اختیاری)                          | ۱.۰.۰+build.۱۰۰ |

### قواعد نسخه‌بندی

| قاعده   | توضیح                                                  |
| ------- | ------------------------------------------------------ |
| PLC-V01 | هر موجودیت عملیاتی یک نسخه جاری دارد                   |
| PLC-V02 | تغییر در OPLC-S01 نیاز به تغییر PATCH دارد             |
| PLC-V03 | تغییر در OPLC-S02 تا OPLC-S03 نیاز به تغییر MINOR دارد |
| PLC-V04 | تغییر ماهیت موجودیت عملیاتی نیاز به تغییر MAJOR دارد   |
| PLC-V05 | نسخه Retired و Archived تغییر نمی‌کنند                 |
| PLC-V06 | همه نسخه‌ها در رجیستری چرخه حیات عملیات ثبت می‌شوند    |
