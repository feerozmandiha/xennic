## ۱. Executive Summary

AI-000 سند مادر معماری عامل‌های هوشمند SMOS است. تمام AI-001 تا AI-014 و هر Agent آینده (تا AI-999) صرفاً از این سند مشتق می‌شوند.

این سند **فقط معماری** را تعریف می‌کند — نه پیاده‌سازی، نه پرامپت، نه workflow، نه ابزار. معماری مستقل از هر فناوری، فروشنده، مدل زبانی، پلتفرم ابری یا API است و برای حداقل ۱۰ سال اعتبار دارد.

### هسته معماری

SMOS از **خانواده‌ای از Agentهای تخصصی** تشکیل شده است که هر کدام یک مسئولیت واحد دارند. Agentها با هم ترکیب می‌شوند (Composition)، نه اینکه توانایی‌ها را تکرار کنند. Orchestrator مرکزی جریان کار را مدیریت می‌کند، اما هر Agent در مرز اختیار خود مستقل عمل می‌کند.

## ۲. Purpose

### هستی‌شناسی سند

AI-000 به‌عنوان **منبع حقیقت واحد (SSOT)** برای تمام جنبه‌های معماری Agentها در SMOS وجود دارد. این سند تعریف می‌کند:

- **یک Agent چیست** — هستی‌شناسی عامل هوشمند در SMOS
- **چگونه Agentها ساخته می‌شوند** — الگوی معماری برای ایجاد Agent جدید
- **چگونه Agentها با هم کار می‌کنند** — قراردادهای ارتباط و همکاری
- **مرزهای Agentها** — اختیار، مسئولیت، محدودیت
- **چرخه حیات Agentها** — از تولد تا بازنشستگی

### جایگاه در سلسله‌مراتب اسناد

```
CON-000  (قانون اساسی — اصول عالی)
  │
ARCH-*   (معماری سیستم — ساختار)
  │
AI-000   ← این سند (معماری Agentها — الگو)
  │
AI-001   (مشخصات Agent استراتژی محتوا)
AI-002   (مشخصات Agent برنامه‌ریزی)
AI-003   (مشخصات Agent تولید محتوا)
...
AI-014   (مشخصات Agent سازمانی — هماهنگ‌ساز عامل‌ها)
AI-014       FAM-05      A-4          LYR-01
  │
PRM-*    (پرامپت‌های اختصاصی هر Agent)
AUT-*    (Workflowهای مربوط به هر Agent)
```

### آنچه AI-000 مالک است

AI-000 تنها مالک موارد زیر است — هر چیز دیگر در اسناد بالادست باقی می‌ماند:

- ✅ معماری Agentها (ساختار، لایه‌ها، روابط)
- ✅ هستی‌شناسی Agent (تعریف، انواع، هویت)
- ✅ قراردادهای Agent (ورودی، خروجی، رابط)
- ✅ مسئولیت‌ها و مرزهای Agent
- ✅ الگوهای همکاری و ارتباط
- ✅ چرخه حیات Agent

## ۵. Design Principles

SMOS بر **۱۲ اصل معماری** برای طراحی Agentها استوار است:

| اصل                              | شناسه | توضیح                                                    |
| -------------------------------- | ----- | -------------------------------------------------------- |
| **AI-First**                     | PR-01 | همه چیز از منظر قابلیت Agent طراحی می‌شود                |
| **Human-First**                  | PR-02 | انسان در رأس سلسله‌مراتب تصمیم قرار دارد                 |
| **Single Responsibility**        | PR-03 | هر Agent دقیقاً یک دلیل برای تغییر دارد                  |
| **Composition over Replication** | PR-04 | Agentها ترکیب می‌شوند، نه اینکه توانایی‌ها را تکرار کنند |
| **Explicit Boundaries**          | PR-05 | هر Agent مرزهای مسئولیت و اختیار صریح دارد               |
| **Self-Contained**               | PR-06 | هر Agent می‌تواند مستقل از دیگران کار کند                |
| **Stateless Contract**           | PR-07 | قراردادهای Agent مستقل از حالت داخلی هستند               |
| **Observable by Default**        | PR-08 | همه اقدامات Agent قابل مشاهده و حسابرسی هستند            |
| **Documentation-Driven**         | PR-09 | Agentها از مستندات به‌عنوان SSOT استفاده می‌کنند         |
| **Graceful Degradation**         | PR-10 | Agentها در صورت خطا به‌جای شکست ناگهانی، تنزل می‌یابند   |
| **Forward Compatibility**        | PR-11 | معماری باید با Agentهای آینده (تا AI-999) سازگار باشد    |
| **Technology Neutrality**        | PR-12 | معماری مستقل از LLM, API, Vendor, Cloud, Runtime است     |

## ۶. Agent Taxonomy

SMOS Agentها را در **۳ بعد** طبقه‌بندی می‌کند:

### بعد ۱ — خانواده (Family)

| خانواده           | شناسه  | توضیح                                   | نمونه Agentها                          |
| ----------------- | ------ | --------------------------------------- | -------------------------------------- |
| **Research**      | FAM-01 | تحقیق، کشف، راستی‌آزمایی، دانش          | AI-005, AI-011, AI-013                 |
| **Content**       | FAM-02 | تولید، نگارش، رسانه، ویدئو، برنامه‌ریزی | AI-002, AI-003, AI-004, AI-006, AI-007 |

### بعد ۲ — سطح اختیار (Authority Level)

| سطح     | شناسه                | توضیح                                            | نمونه                   |
| ------- | -------------------- | ------------------------------------------------ | ----------------------- |
| **A-0** | No Authority         | بدون اختیار                                      | —                       |

| **A-4** | Fully Autonomous     | اقدام خودکار کامل (تنها اقدامات از پیش تأییدشده) | Data Collection         |

### بعد ۳ — لایه عملیاتی (Operational Layer)

| لایه            | شناسه  | توضیح                                   |
| --------------- | ------ | --------------------------------------- |
| **Strategic**   | LYR-01 | تصمیمات سطح بالا — نیاز به تأیید انسانی |

| **Operational** | LYR-03 | اجرا و تولید — خودکار با نظارت          |
| **Support**     | LYR-04 | پشتیبانی و زیرساخت — کاملاً خودکار      |

### قواعد طبقه‌بندی

1. هر Agent دقیقاً به یک خانواده تعلق دارد
2. هر Agent یک سطح اختیار دارد (ثابت، قابل تغییر با ADR)
3. هر Agent یک لایه عملیاتی دارد
4. خانواده‌ها می‌توانند در آینده گسترش یابند (FAM-06, ...)
5. تغییر خانواده یک Agent نیاز به ADR دارد

## ۸. Capability Model

توانایی‌های Agent در SMOS به صورت **سلسله‌مراتبی** تعریف می‌شوند:

### سطوح توانایی

| سطح                       | شناسه  | توضیح                             | مثال                            |
| ------------------------- | ------ | --------------------------------- | ------------------------------- |
| **Core Capability**       | CAP-01 | توانایی ذاتی Agent — دلیل وجود آن | تدوین استراتژی برای AI-001      |
| **Supporting Capability** | CAP-02 | توانایی کمکی برای انجام Core      | تحلیل Gap برای AI-001           |
| **Reflexive Capability**  | CAP-04 | توانایی خودارزیابی                | خودارزیابی استراتژی برای AI-001 |

### مدل توانایی

```
هر Agent:
  └── 1 Core Capability (اجباری)
       └── N Supporting Capabilities (اختیاری، ۰ تا N)
            └── M Collaborative Capabilities (اختیاری، ۰ تا M)
                 └── 1 Reflexive Capability (اجباری)
```

### قواعد توانایی

| قاعده                                                       | شناسه   | توضیح                 |
| ----------------------------------------------------------- | ------- | --------------------- |
| هر Agent دارای دقیقاً یک Core Capability است                | CAP-R01 | تک‌مسئولیتی           |
| Supporting Capabilities فقط Core را پشتیبانی می‌کنند        | CAP-R02 | عدم انحراف از مأموریت |
| Collaborative Capabilities فقط با Agentهای مجاز کار می‌کنند | CAP-R03 | امنیت ارتباط          |
| Reflexive Capability برای همه Agentها اجباری است            | CAP-R04 | شفافیت                |
| توانایی‌ها مستند می‌شوند نه پیاده‌سازی                      | CAP-R05 | معماری محض            |

## ۱۱. Context Model

زمینه (Context) یک Agent شامل تمام اطلاعاتی است که برای انجام وظیفه نیاز دارد.

### لایه‌های زمینه

```
┌──────────────────────────────────────────────────────────────┐
│  GLOBAL CONTEXT     (سیستم: CON-000, ARCH-*, GOV-*, ...)     │
│  — برای همه Agentها یکسان — ثابت در طول عمر سیستم             │
├──────────────────────────────────────────────────────────────┤
│  FAMILY CONTEXT     (خانواده: قواعد مشترک خانواده)             │
│  — برای همه Agentهای یک خانواده یکسان                         │
├──────────────────────────────────────────────────────────────┤
│  SESSION CONTEXT    (جلسه: Task, Input, Parameters)           │
│  — منحصر به یک وظیفه — متغیر در هر بار اجرا                   │
├──────────────────────────────────────────────────────────────┤
│  LOCAL CONTEXT      (محلی: حالت داخلی Agent)                  │
│  — فقط متعلق به خود Agent                                    │
└──────────────────────────────────────────────────────────────┘
```

### انواع زمینه

| نوع                       | شناسه  | منبع             | به‌روزرسانی       |
| ------------------------- | ------ | ---------------- | ----------------- |
| **System Context**        | CTX-01 | مستندات SSOT     | به‌روزرسانی سیستم |
| **Task Context**          | CTX-02 | ورودی وظیفه      | هر وظیفه          |
| **Agent Context**         | CTX-03 | حافظه Agent      | مستمر             |
| **Knowledge Context**     | CTX-04 | KNW-\*, ARCH-012 | در صورت نیاز      |
| **Collaboration Context** | CTX-05 | Agent دیگر       | در حین همکاری     |

### قواعد زمینه

1. Global Context برای همه Agentها در دسترس است
2. هر Agent فقط به Context مورد نیاز خود دسترسی دارد (Least Privilege)
3. Session Context پس از اتمام وظیفه پاک می‌شود (مگر در Memory)
4. Agentها نمی‌توانند Context یکدیگر را مستقیماً بخوانند
5. Context باید قابل ارجاع (Referenceable) باشد

## ۱۲. Memory Model

SMOS از **۳ نوع حافظه** برای Agentها پشتیبانی می‌کند:

### انواع حافظه

| نوع                 | شناسه  | توضیح                                    | ماندگاری       | دسترسی           |
| ------------------- | ------ | ---------------------------------------- | -------------- | ---------------- |
| **Working Memory**  | MEM-01 | حافظه کوتاه‌مدت — برای وظیفه جاری        | طول یک Task    | فقط Agent خود    |
| **Episodic Memory** | MEM-02 | حافظه میان‌مدت — تجربیات و تحقیقات گذشته | هفته‌ها/ماه‌ها | Agent خود + مجوز |
| **Semantic Memory** | MEM-03 | حافظه بلندمدت — دانش ساختاریافته         | سال‌ها         | همه Agentها      |

### معماری حافظه

```
┌─────────────────────────────────────────────────────────────┐
│                    WORKING MEMORY                             │
│  Task Input · Current State · Intermediate Results          │
│  └── پس از اتمام Task: پاک می‌شود (یا به Episodic می‌رود)    │
├─────────────────────────────────────────────────────────────┤
│                    EPISODIC MEMORY                            │
│  Past Tasks · Decisions · Errors · Outcomes                 │
│  └── جستجو: بر اساس شباهت (Similarity Search)                │
├─────────────────────────────────────────────────────────────┤
│                    SEMANTIC MEMORY                            │
│  KNW-* · ARCH-* · GOV-* · BRD-* · EDT-* · PLAT-*           │
│  └── SSOT: فقط از مستندات تغذیه می‌شود                      │
└─────────────────────────────────────────────────────────────┘
```

### قواعد حافظه

| قاعده                                                    | شناسه   | توضیح |
| -------------------------------------------------------- | ------- | ----- |
| هیچ Agentی حافظه اختصاصی ندارد مگر در Working Memory     | MEM-R01 |       |
| Episodic Memory می‌تواند توسط Agent خود نوشته شود        | MEM-R02 |       |
| Semantic Memory فقط توسط AI-011 (Knowledge) نوشته می‌شود | MEM-R03 |       |
| حافظه باید قابل Audit باشد                               | MEM-R04 |       |
| حافظه منسوخ باید منقضی (Expire) شود                      | MEM-R05 |       |

## ۱۵. Communication Architecture

Agentها در SMOS از طریق یک **اتوبوس رویداد (Event Bus)** معماری با هم ارتباط برقرار می‌کنند.

### مدل ارتباطی

```
┌─────────────────────────────────────────────────────────────┐
│                      EVENT BUS                                │
│  publish(event) / subscribe(event, handler)                 │
└─────────────────────────────────────────────────────────────┘
         │                │                │
         ▼                ▼                ▼
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ Agent-1  │    │ Agent-2  │    │ Agent-3  │
   │ Publisher│    │Consumer │    │Consumer  │
   └──────────┘    └──────────┘    └──────────┘
```

### انواع ارتباط

| نوع          | شناسه  | توضیح                      | مثال                 |
| ------------ | ------ | -------------------------- | -------------------- |
| **Event**    | COM-01 | انتشار رویداد — یک‌طرفه    | research.completed   |
| **Command**  | COM-02 | دستور — دوطرفه با تأیید    | orchestrator → agent |
| **Query**    | COM-03 | پرس و جو — درخواست اطلاعات | agent → knowledge    |
| **Response** | COM-04 | پاسخ — به Command یا Query | agent → orchestrator |

### قواعد ارتباطی

| قاعده                                               | شناسه   | توضیح |
| --------------------------------------------------- | ------- | ----- |
| ارتباط صرفاً از طریق Event Bus انجام می‌شود         | COM-R01 |       |
| Agentها هرگز مستقیماً با هم ارتباط ندارند           | COM-R02 |       |
| همه ارتباطات قابل ردیابی (Auditable) است            | COM-R03 |       |
| Agentها باید تأیید دریافت (Acknowledgement) بفرستند | COM-R04 |       |
| پیام‌ها دارای انقضا (TTL) هستند                     | COM-R05 |       |

## ۱۶. Collaboration Architecture

### مدل‌های همکاری

## ۱۸. Escalation Rules

ارجاع (Escalation) زمانی رخ می‌دهد که Agent از مرز اختیار یا توانایی خود خارج شود.

### سلسله‌مراتب Escalation

```
Level 1: Agent → Human Operator
    └── شرایط: اطمینان < آستانه, خطای غیرمنتظره, نیاز به مجوز
Level 2: Human Operator → Content Manager
    └── شرایط: ریسک > R-2, نیاز به تخصص بالاتر
Level 3: Content Manager → Media Director
    └── شرایط: ریسک > R-3, تأثیر بر برند
Level 4: Media Director → System Architect
    └── شرایط: ریسک > R-4, تغییر معماری
Level 5: System Architect → CEO
    └── شرایط: ریسک R-5, بحران سازمانی
```

### انواع Escalation

| نوع                       | شناسه  | توضیح                | اقدام                    |
| ------------------------- | ------ | -------------------- | ------------------------ |
| **Confidence Escalation** | ESC-01 | اطمینان زیر آستانه   | درخواست تأیید انسانی     |
| **Scope Escalation**      | ESC-02 | خارج از محدوده وظیفه | درخواست شفاف‌سازی        |
| **Permission Escalation** | ESC-03 | نیاز به دسترسی بیشتر | درخواست مجوز             |
| **Error Escalation**      | ESC-04 | خطای غیرقابل حل      | اطلاع و درخواست راهنمایی |
| **Conflict Escalation**   | ESC-05 | تناقض در منابع       | اطلاع به معمار           |
| **Risk Escalation**       | ESC-06 | ریسک بالای برند      | ارسال به مدیر برند       |

### قواعد Escalation

| قاعده                                          | شناسه   | توضیح |
| ---------------------------------------------- | ------- | ----- |
| Agent باید دلیل Escalation را مستند کند        | ESC-R01 |       |
| Agent باید گزینه‌های پیشنهادی خود را ارائه دهد | ESC-R02 |       |
| Escalation سطح ۱ می‌تواند خودکار حل شود        | ESC-R03 |       |
| Escalation سطح ≥ ۳ نیاز به ADR دارد            | ESC-R04 |       |
| زمان پاسخ Escalation باید مشخص باشد            | ESC-R05 |       |

## ۱۹. Human Override

انسان در هر لحظه می‌تواند تصمیمات Agent را override کند.

### انواع Override

| نوع                    | شناسه  | توضیح                    | سطح مجاز         |
| ---------------------- | ------ | ------------------------ | ---------------- |
| **Soft Override**      | OVR-01 | پیشنهاد جایگزین به Agent | Human Operator   |
| **Hard Override**      | OVR-02 | رد قطعی خروجی Agent      | Content Manager  |
| **Emergency Override** | OVR-03 | توقف فوری Agent          | Media Director   |
| **System Override**    | OVR-04 | تغییر موقت معماری        | System Architect |

### فرایند Override

```
1. شناسایی: انسان یا Agent مشکل را شناسایی می‌کند
2. تصمیم: انسان نوع Override را انتخاب می‌کند
3. اجرا: Override اعمال می‌شود
4. ثبت: در Audit Log + ADR (برای Hard و بالاتر)
5. بررسی: علت ریشه‌ای تحلیل می‌شود
6. پیشگیری: قاعده جدید به معماری اضافه می‌شود
```

### قواعد Override

| قاعده                                         | شناسه   | توضیح |
| --------------------------------------------- | ------- | ----- |
| هر Override باید ثبت شود                      | OVR-R01 |       |
| Soft Override نیازی به مستندات اضافی ندارد    | OVR-R02 |       |
| Hard Override باید در ADR ثبت شود             | OVR-R03 |       |
| Emergency Override باید ظرف ۲۴ ساعت مستند شود | OVR-R04 |       |
| System Override نیاز به جلسه معماری دارد      | OVR-R05 |       |
| Overrideهای مکرر نشانه مشکل معماری است        | OVR-R06 |       |

## ۲۰. Governance

حکمرانی Agentها بر اساس **ARCH-030** و **ARCH-032** با جزئیات زیر اعمال می‌شود.

### مدل مالکیت Agentها

هر Agent دارای ۶ نقش مالکیتی است (مطابق ARCH-030 §۴):

| نقش                        | مسئولیت          | انتصاب توسط |
| -------------------------- | ---------------- | ----------- |
| **Owner (مالک)**           | پاسخگویی نهایی   | مدیر ارشد   |
| **Custodian (نگهبان)**     | مدیریت روزمره    | Owner       |
| **Maintainer (نگهدارنده)** | به‌روزرسانی      | Custodian   |
| **Reviewer (بازبین)**      | بازبینی تغییرات  | Owner       |
| **Approver (تأییدکننده)**  | تأیید نهایی      | Owner       |
| **Consumer (مصرف‌کننده)**  | استفاده از Agent | سیستم       |

### ماتریس RACI پیشنهادی برای AI-\*

| فعالیت                 | System Architect | AI Gov Mgr | Automation Eng | Human Operator | AI Agent |
| ---------------------- | ---------------- | ---------- | -------------- | -------------- | -------- |
| **تعریف معماری Agent** | A/R              | C          | C              | —              | —        |
| **ایجاد Agent جدید**   | A                | R          | C              | C              | —        |
| **به‌روزرسانی Agent**  | I                | A/R        | C              | C              | C        |
| **تأیید خروجی Agent**  | —                | C          | —              | A/R            | C        |
| **تغییر سطح اختیار**   | A/R              | C          | —              | —              | —        |
| **بازنشستگی Agent**    | A/R              | C          | C              | C              | —        |
| **حسابرسی Agent**      | I                | A/R        | —              | —              | C        |

### قواعد حکمرانی Agent

1. هر Agent یک Owner انسانی دارد
2. ایجاد Agent جدید نیاز به ADR دارد
3. تغییر سطح اختیار Agent نیاز به ADR دارد
4. بازنشستگی Agent نیاز به تأیید Owner دارد
5. همه تغییرات Agent در Change Log ثبت می‌شود

## ۲۱. Security

### اصول امنیتی Agentها

| اصل                   | شناسه  | توضیح                                             |
| --------------------- | ------ | ------------------------------------------------- |
| **Least Privilege**   | SEC-01 | هر Agent فقط به حداقل منابع مورد نیاز دسترسی دارد |
| **Defense in Depth**  | SEC-02 | امنیت در چند لایه                                 |
| **Secure by Default** | SEC-03 | پیش‌فرض امن، باز کردن با مجوز                     |
| **Auditable**         | SEC-04 | همه دسترسی‌ها قابل ردیابی                         |
| **Isolation**         | SEC-05 | Agentها از هم جدا هستند                           |

### مرزهای امنیتی

```
┌─────────────────────────────────────────────────────────────┐
│  SECURITY BOUNDARY 1: External Access                        │
│  ┌─ → اینترنت, APIs خارجی, Web Search                         │
│  └─ → فقط Agentهای مجاز (AI-001, AI-005)                     │
├─────────────────────────────────────────────────────────────┤
│  SECURITY BOUNDARY 2: Knowledge Access                       │
│  ┌─ → KNW-*, REP-*, ARCH-*                                   │
│  └─ → سطح دسترسی بر اساس نوع Agent                          │
├─────────────────────────────────────────────────────────────┤
│  SECURITY BOUNDARY 3: Agent Communication                     │
│  ┌─ → Event Bus                                              │
│  └─ → احراز هویت پیام‌ها                                     │
├─────────────────────────────────────────────────────────────┤
│  SECURITY BOUNDARY 4: Human Interface                         │
│  ┌─ → Override, Escalation, Approval                         │
│  └─ → احراز هویت انسان                                       │
└─────────────────────────────────────────────────────────────┘
```

### اقدامات ممنوعه امنیتی (Security Forbidden)

| شناسه       | اقدام ممنوع                       | مجازات               |
| ----------- | --------------------------------- | -------------------- |
| SEC-FORB-01 | دسترسی به حافظه Agent دیگر        | غیرفعال‌سازی Agent   |
| SEC-FORB-02 | تغییر سطح دسترسی خود              | غیرفعال‌سازی Agent   |
| SEC-FORB-03 | ارسال پیام جعلی به نام Agent دیگر | غیرفعال‌سازی Agent   |
| SEC-FORB-04 | دور زدن Audit Log                 | غیرفعال‌سازی دائمی   |
| SEC-FORB-05 | دسترسی به داده‌های شخصی بدون مجوز | غیرفعال‌سازی + گزارش |

## ۲۸. Change Management

تغییرات در معماری Agentها بر اساس **ARCH-031** و با فرایند زیر مدیریت می‌شود.

### انواع تغییر

| نوع                  | شناسه  | توضیح                                | فرایند                 |
| -------------------- | ------ | ------------------------------------ | ---------------------- |
| **Minor Change**     | CHG-01 | ویرایش توضیحات، اصلاح ارجاع          | بدون ADR               |
| **Major Change**     | CHG-02 | اضافه کردن Agent جدید، تغییر خانواده | ADR + Gate             |
| **Critical Change**  | CHG-03 | تغییر معماری Agent، سطح اختیار       | ADR + Gate + Architect |
| **Emergency Change** | CHG-04 | رفع بحران امنیتی                     | Fast Track + ADR بعدی  |

### فرایند تغییر

```
1. شناسایی نیاز به تغییر
2. تعیین نوع تغییر (CHG-01 تا CHG-04)
3. Minor → اعمال مستقیم
   Major → ایجاد ADR + عبور از ۷ گیت
   Critical → ADR + عبور از ۷ گیت + تأیید معمار
   Emergency → Fast Track + ADR ظرف ۲۴ ساعت
4. به‌روزرسانی AI-000 یا AI-NNN
5. ثبت در Change Log
6. اعلام به مصرف‌کنندگان
```

### قواعد تغییر

| قاعده                                          | شناسه   | توضیح |
| ---------------------------------------------- | ------- | ----- |
| Minor Change نیازی به ADR ندارد                | CHG-R01 |       |
| Major Change نیاز به ADR دارد                  | CHG-R02 |       |
| Critical Change نیاز به ADR + تأیید معمار دارد | CHG-R03 |       |
| همه تغییرات در Change Log ثبت می‌شوند          | CHG-R04 |       |
| تغییرات باید backward compatible باشند         | CHG-R05 |       |

## ۲۹. Reading Guide

این سند توسط موجودیت‌های مختلف به روش‌های مختلف خوانده می‌شود:

### برای معمار سیستم

از **§۲ (Purpose)** و **§۴ (Enterprise Agent Architecture)** شروع کنید. سپس **§۵ (Design Principles)** و **§۶ (Agent Taxonomy)** را بخوانید. برای ایجاد Agent جدید از **§۷ (Identity Model)**, **§۸ (Capability Model)**, **§۹ (Responsibility Model)** به‌عنوان الگو استفاده کنید. **§۲۸ (Change Management)** فرایند تغییر را مشخص می‌کند.

### برای پیاده‌کننده Agent

از **§۱۱ (Context Model)** و **§۱۲ (Memory Model)** برای درک معماری داخلی Agent شروع کنید. **§۱۵ (Communication Architecture)**, **§۱۶ (Collaboration Architecture)**, **§۱۷ (Delegation Rules)**, **§۱۸ (Escalation Rules)** نحوه تعامل Agent را مشخص می‌کنند. **§۲۴ (Validation Rules)** و **§۲۵ (Quality Gates)** محدودیت‌ها را تعیین می‌کنند.

### برای حکمران AI

از **§۱۰ (Decision Authority)** و **§۱۹ (Human Override)** و **§۲۰ (Governance)** شروع کنید. سپس **§۲۱ (Security)** و **§۲۲ (Audit & Traceability)** را بخوانید. **§۲۳ (Performance Metrics)** برای نظارت بر عملکرد استفاده می‌شود.

### برای طراح Agent جدید (AI-NNN)

از **§۲۶ (Machine Readable Blocks)** و **§۲۷ (JSON Schemas)** برای ایجاد بلوک‌های استاندارد استفاده کنید. سپس با الگوی ۲۷ بخشی AI-001 (یا نسخه به‌روزشده) مشخصات Agent جدید را بنویسید. **§۲۵ (Quality Gates)** مراحل تصویب را مشخص می‌کند.
